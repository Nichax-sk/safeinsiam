# CLAUDE.md

Guidance for Claude Code when working in this repository.

## 1. Project overview

SafeInSiam is a monorepo laid out as follows:

- `frontend/`: Nuxt 4 web app
- `backend/`: Go API built on Gin
- `docker-compose.yml` (repo root): defines the PostgreSQL service
- `database/`: set aside for database-related files. It currently holds only the empty `migrations/` and `seeds/` folders.

The project is an early scaffold. The backend has only health-check endpoints and the frontend has one placeholder page. Product features and requirements are not defined in the repo yet, so don't assume them.

## 3. Backend (`backend/`)

Go module `github.com/Nichax-sk/safeinsiam`, `go 1.27.3`.

| Dependency | Version |
|---|---|
| github.com/gin-gonic/gin | v1.12.0 |
| github.com/jackc/pgx/v5 (pgxpool) | v5.12.0 |
| github.com/joho/godotenv | v1.5.1 |

Layout:

- `cmd/api/main.go`: entrypoint. Loads config, builds the logger, sets up SIGINT/SIGTERM handling (a second signal force-quits), calls `app.Run`, and is the only place that calls `os.Exit`.
- `internal/app/app.go`: `Run(ctx, cfg, logger) error` wires the DB pool and router, listens synchronously (so a port conflict returns an error), serves until `ctx` is cancelled, drains in-flight requests within `SHUTDOWN_TIMEOUT`, then closes the pool. The HTTP server timeouts are constants: read header 5s, read 15s, write 30s, idle 60s, max header 1 MiB.
  `app.go` also maps `APP_ENV` to Gin mode and builds the HTTP handler in `newHandler`: the router with `DebugRoutes: health.Routes`, plus `health.Register(router.Engine, db)`.
- `internal/httpapi/router.go`: `NewRouter(Options{Logger, DebugRoutes, CORSAllowedOrigins, TrustedProxies})` returns `Router{Engine, V1}`. It sets up the shared middleware in this order: request ID, then security headers, then the slog request logger, then CORS (only when origins are configured), then panic recovery. It also configures trusted proxies (none by default; client IPs read from `X-Forwarded-For` only), sets up JSON 404 (`NoRoute`) and 405 (`NoMethod`, with Gin's `Allow` header), and creates the empty `/api/v1` group (`V1`) where versioned API routes register. `httpapi` never imports feature packages; it imports `internal/database` only to map database errors.
- `internal/httpapi/requestid.go`: the request ID middleware and `RequestIDFromContext(ctx)`.
- `internal/httpapi/recovery.go`: slog-based panic recovery, which replaces `gin.Recovery`.
- `internal/httpapi/security.go`: `securityHeaders()`, the only code that sets the global security headers.
- `internal/httpapi/cors.go`: the CORS middleware and `addVary`.
- `internal/httpapi/errors.go`, `respond.go`: the API error type (`Error`, `NewError`, `Code`), `WriteJSON` and `WriteError`.
- `internal/httpapi/dberror.go`: `DatabaseError(err)`, which maps classified database errors to API errors.
- `internal/health/handler.go`: `Register(r, db Pinger)` adds the health routes at `PathLive` (`/health`) and `PathDB` (`/health/db`). `Routes` lists both, for logging configuration.
- `internal/config/config.go`: reads and validates environment variables, reporting every error at once. Outside production it reads an env file (`ENV_FILE`, default `../.env` relative to the working directory) without modifying the process environment. Non-empty process variables take precedence over file values.
- `internal/database/postgres.go`: `NewPostgresPool` builds the pgx config from a `net/url` URL (never a formatted DSN), sets `application_name` and `statement_timeout`, and pings with bounded retry: 5 attempts, backoff 0.5s→4s, cancelled by `ctx`. MaxConnLifetime 1h, MaxConnIdleTime 30m, HealthCheckPeriod 1m.
- `internal/database/errors.go`: `Classify` and `IsRetryable` for pgx/PostgreSQL errors (see Database errors below).
- `internal/logging/logging.go`: `log/slog` logger. Text in development and test, JSON in staging and production.

Routes:

- `GET /health`: liveness check
- `GET /health/db`: pings the database (3s timeout); returns 503 if it can't connect
- `/api/v1/*`: no routes yet

The health responses (`{"status":…,"message":…}`) predate the error envelope and are kept unchanged for compatibility. Every other error response, including 404 and 405, uses the envelope:

```json
{"error":{"code":"not_found","message":"Resource not found","request_id":"3QX7…","details":[]}}
```

`request_id` is the request's ID (see Request ID below). Codes and statuses: `bad_request` 400, `unauthorized` 401, `forbidden` 403, `not_found` 404, `method_not_allowed` 405, `conflict` 409, `payload_too_large` 413, `unsupported_media_type` 415, `validation_failed` 422, `too_many_requests` 429, `internal_error` 500, `service_unavailable` 503.

Request ID:

- **Inbound:** a request's `X-Request-ID` is kept only if there is exactly one such header and it matches `^[A-Za-z0-9._-]{1,64}$`. Otherwise a new ID is generated with `crypto/rand.Text()`.
- **One ID everywhere:** the ID is stored in the request context, set on the response's `X-Request-ID` header before any handler runs, and used in the error envelope's `request_id` and the access log. All of these read the same value.
- **Correlation only:** clients can choose their own ID, so never use it for authorization, deduplication or idempotency.

Access log: exactly one entry per request. Fields:

| Field | Meaning |
|---|---|
| `method` | HTTP method |
| `route` | The route template, or the path when unmatched |
| `status` | Response status |
| `latency_ms` | Float, milliseconds |
| `client_ip` | Client address |
| `bytes` | Response body size; 0 when no body was written |
| `request_id` | The request ID |

Levels:

| Response | Level |
|---|---|
| 5xx | Error |
| 4xx | Warn |
| Successful (below 400) requests to `DebugRoutes`, i.e. the health routes | Debug (hidden at the default `LOG_LEVEL=info`) |
| Everything else | Info |

For 5xx responses written by `WriteError`, the entry also gets `error_code`, plus `error_type` when there's a cause (the Go type names in the error chain). It never logs error text, query strings, headers or request bodies.

Panic recovery (in `recovery.go`):

- **Response:** a recovered panic gets the standard 500 `internal_error` envelope with the request ID. If the response has already started, it is left unchanged.
- **Logs:** each panic produces exactly one `"panic recovered"` Error entry plus the request's single access entry (with `error_code=internal_error` and `error_type=httpapi.panicError`). Both carry the same `request_id`.
- **Panic log fields:** `request_id`, `method`, `route`, `panic_type` and `stack`.
  - `panic_type` is the value's Go type (`%T`).
  - `stack` is capped at 16 KiB.
- **Never logged:** the panic value's text. Recovery never calls `Error()`, `String()` or any formatting method on a recovered value (application types can implement them, including `runtime.Error`, and may leak secrets or panic). Headers, query strings and bodies aren't logged either.
- **`http.ErrAbortHandler`:** a panic that is or wraps it is re-panicked as the bare sentinel, so `net/http` aborts the connection silently. It produces no logs.

Security headers (in `security.go`): every response written through the middleware chain carries exactly one of each:

- `X-Content-Type-Options: nosniff`
- `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`
- `X-Frame-Options: DENY`

That covers success, errors, 404/405, `HEAD`, empty bodies and recovered panics. `securityHeaders()` sets them before any handler runs, right after the request ID middleware.

- **Scope:** the CSP and `X-Frame-Options` are defense in depth for this backend's responses only. They do **not** secure the separate Nuxt frontend; its security headers belong to the frontend and its hosting.
- **Not set by the backend:**
  - `Strict-Transport-Security`, which belongs at the TLS-terminating proxy. The app serves plain HTTP and trusts no proxies.
  - `Referrer-Policy` and `Permissions-Policy`, which don't apply to JSON responses.
  - `Cache-Control`, to be decided per route when feature routes arrive.
- **Ownership:** a test fails if any non-test Go file other than `security.go` names these headers.

CORS (in `cors.go`, installed only when `CORS_ALLOWED_ORIGINS` is set):

- **Origins:** configured origins are canonicalized (lowercase scheme and host, `:80`/`:443` default ports removed, other ports kept). A request matches only if it has exactly one `Origin` header exactly equal to a configured origin; `null`, multiple or comma-joined values never match. The response's `Access-Control-Allow-Origin` is that configured origin, never a reflected header.
- **Fixed policy:**
  - Methods: `GET, POST, PUT, PATCH, DELETE`.
  - Request headers: `Content-Type, X-Request-ID`.
  - Exposed headers: `X-Request-ID`.
  - Preflight `Max-Age`: 600.
  - **Credentials are never allowed.**
- **Allowed origin, non-preflight:** every response through the chain (including errors, 404/405 and recovered panics) carries `Access-Control-Allow-Origin` and `Access-Control-Expose-Headers`. Preflights are answered separately (below).
- **Disallowed origin:** the request is served normally without CORS headers, so the browser blocks the read.
- **Preflight** means `OPTIONS` with an `Origin` header and an `Access-Control-Request-Method` header, even an empty one.
  - **Valid preflight → 204.** Valid means the origin is allowed; the requested method is a single valid token that exactly (case-sensitively) matches an allowed method; and every requested header is allowed (compared case-insensitively). The 204 carries `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers`, `Access-Control-Max-Age` and `Vary`, but not `Access-Control-Expose-Headers`.
  - **Anything else → 403** standard envelope (`forbidden`, "CORS request not allowed"), without `Access-Control-Allow-Origin`.
  - **`OPTIONS` without `Access-Control-Request-Method`** is an ordinary request (404/405).
  - **Use uppercase `PATCH` in frontend code:** browsers uppercase most methods but send `patch` as written.
- **`Vary`:** `Origin` is added to every response (and the two `Access-Control-Request-*` tokens on preflights) without removing existing `Vary` values or duplicating tokens.
- **CORS is not authorization.** Simple cross-origin requests still reach handlers. CSRF protection belongs with authentication.

Trusted proxies (`TRUSTED_PROXIES`):

- **Empty (the default):** forwarded headers are ignored and the client IP is the connection's remote address. Gin's own default would trust every proxy, so `NewRouter` always sets the list explicitly.
- **Configured:** the client IP is the rightmost `X-Forwarded-For` entry that isn't a trusted proxy. `X-Real-IP` and other headers are never used.
- **Validation:** entries are canonicalized to CIDRs (bare IPs become `/32` or `/128`; IPv4-mapped forms become IPv4) so Gin interprets them exactly as validated. Any configuration whose networks **together** cover all IPv4 or all IPv6 addresses is rejected: single entries such as `0.0.0.0/0`, `::/0` or `::ffff:0:0/96`, and combinations such as `0.0.0.0/1,128.0.0.0/1` or `::/1,8000::/1`.
- **Set it only to the real reverse proxies' addresses.**

Database errors (`database/errors.go`, `httpapi/dberror.go`):

- **`database.Classify(err)`** returns a `Kind` (unknown, not_found, conflict, contention, unavailable, timeout, canceled), `Retryable` and the `SQLState`. It inspects the error chain and uses exact SQLSTATE codes (PostgreSQL 17 Appendix A; no prefix or message matching). It never wraps or changes the error.
- **Order:** nil/typed-nil chain → context cancel → timeout (deadline, `pgconn.Timeout`, timeout `net.Error`) → `*pgconn.PgError` → `pgx.ErrNoRows` → `*pgconn.ConnectError`/`ErrConnClosed`/`pgconn.SafeToRetry` → unknown. A chain holding a typed-nil error or a cycle, or exceeding the search budget, is unknown.
- **Search budget** (`Classify` and `DatabaseError` alike): identified errors (pointers, maps, channels) count once per identity, so shared references are counted once; errors without a stable identity, such as non-pointer values, count on every visit. The search stops when the total counted visits exceed 256.
- **Retryable** means retrying the whole operation unchanged may succeed and is known not to duplicate effects. Only:
  - `40001`, `40P01`, `55P03` (ERROR level, so the transaction is aborted) and `57P05` (idle session);
  - `57P03` and `53300`, **only** with a `*pgconn.ConnectError` in the chain (session startup);
  - a `*pgconn.ConnectError` with no `PgError` in its chain, or `pgconn.SafeToRetry`.

  Not retryable: class 08 (`08000`–`08007`), `57P01`, `57P02`, `53000`, `53200`, `40003`, `57014`, other timeouts and network errors. Unknown codes and errors are not marked retryable.
- **No automatic retries.** `IsRetryable` only reports; the startup ping's own bounded retry is separate and unchanged.
- **`httpapi.DatabaseError(err)`** maps for `WriteError`: not_found → 404, conflict (`23505`, `23503`, `23P01`, `23001`) → 409, contention/unavailable/timeout/canceled → 503 `service_unavailable`, unknown (including `23502`, `23514`, `22xxx`) → 500. It uses default messages and no details, and keeps the error as the cause.
- **Existing API errors:** `DatabaseError` first searches the chain, depth first in `errors.As` order, for a non-nil `*httpapi.Error`, and returns the error unchanged if it finds one.
  - Shared identified errors are searched once.
  - The search stops on a cycle, or when it exceeds the search budget.
  - If the search stops before finding an `*httpapi.Error`, `DatabaseError` wraps the original error as `internal_error`.
- **Disclosure:** raw error and driver text are never written to request logs or API responses: no PostgreSQL messages, details, hints, SQL, schema/table/column/constraint names, hosts or users. 5xx request-log entries represent the error only by its `error_code` and the Go type names in its chain.
  - **Exception, startup logs:** `database not ready, retrying` and the final startup error print pgx error text. It can include the DB host, user and database name, but never the password.

Known gaps:

- **Trailing-slash redirects** (e.g. `/health/` → `/health`): Gin writes these before any middleware runs, so they have no `X-Request-ID`, no security headers, no CORS headers and no log entry.
- **`net/http` protocol errors** (e.g. a malformed request's 400, or 431 for oversized headers): `net/http` writes these before the handler runs, so they carry no security headers, CORS headers or request ID.

## 4. Environment configuration

- **The root `.env` is the single source of truth.** Docker Compose and the Go backend both read it and use the same variable names (`POSTGRES_*`, `DB_HOST`, `DB_SSLMODE`, `APP_ENV`, `APP_PORT`).
- **The root `.env.example` is the setup template.** Copy it to `.env` only if the root `.env` does not exist yet, then replace the placeholder `POSTGRES_PASSWORD` with a secure password. Never overwrite an existing `.env`: it may hold the user's real local credentials. See Section 6 for the full local development steps.
- `backend/.env.example` lists the same keys for reference. The backend doesn't load a `backend/.env`.
- The backend loads `../.env` relative to its working directory, so it **must be started from `backend/`** (or set `ENV_FILE` to the file's path). Non-empty variables already set in the process environment override values from the file. No env file is read when `APP_ENV=production`. `APP_ENV=production` must come from the process environment; if it is read from an env file, startup fails.
- `.env` is gitignored. Never commit, stage, print, or overwrite it.

## 5. Database

- `docker-compose.yml` runs one service, `postgres` (`postgres:17-alpine`).
- It binds to `127.0.0.1:${POSTGRES_PORT:-5432}`, stores data in the named volume `postgres_data`, and has a `pg_isready` healthcheck.
- Credentials come from the root `.env` (`POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_PORT`), the same file the backend reads.
- `database/migrations/` and `database/seeds/` exist but are empty (and untracked). No migration tool has been chosen yet.

## 6. Local development

**One-time setup (from repository root, only if the root `.env` does not exist yet):** create the root `.env` from the template:

```bash
cp .env.example .env
```

Then, in the new `.env`, replace the placeholder `POSTGRES_PASSWORD` with a secure password.

> **Warning:** If a root `.env` already exists, do **not** run the copy command. Never overwrite an existing `.env`: it may hold the user's real local credentials.

Run each service in its own terminal, in this order. Open every terminal at the repository root: the `cd backend` and `cd frontend` commands below are relative to it. The backend and frontend keep running in the foreground.

**Terminal 1 — Database (from repository root):**

```bash
docker compose up -d
```

**Terminal 2 — Backend (from repository root):**

```bash
cd backend
go run ./cmd/api
```

The backend has to run from `backend/` because it loads `../.env` relative to its working directory.

**Terminal 3 — Frontend (from repository root):**

```bash
cd frontend
npm install
npm run dev
```

`npm install` runs `nuxt prepare` as a postinstall step.

Local URLs:

- Backend: http://127.0.0.1:8080 (health checks: `/health`, `/health/db`)
- Frontend: http://localhost:3000

## 8. Coding conventions (as seen in the existing code)

- Go: application packages live under `backend/internal/`.
- Go: wrap errors with context, e.g. `fmt.Errorf("create database pool: %w", err)`.
- Go: put a `context.WithTimeout` on every DB call (health ping 3s, startup ping 5s).
- Go HTTP: register versioned API routes on `router.V1` and send every error response through `httpapi.WriteError`. Return client errors as `httpapi.NewError(code, message)`; the HTTP status is derived from the code. Any other error becomes a 500 `internal_error` with a fixed message. Don't log errors in handlers: `WriteError` records 5xx causes for the request logger, which logs each request once. Read the request ID with `httpapi.RequestIDFromContext(ctx)`; never generate one elsewhere.
- Go HTTP security headers: only `securityHeaders()` in `internal/httpapi/security.go` sets `X-Content-Type-Options`, `Content-Security-Policy` and `X-Frame-Options`. Handlers and helpers must not set, change or remove them. Change the policy only by editing `security.go`, as a reviewed change; never override it per handler.
- Go HTTP `Vary`: handlers that vary responses must use `c.Writer.Header().Add("Vary", …)`, never `Set`, so the CORS `Vary` values are kept.
- Go database errors: send them through `httpapi.WriteError(c, httpapi.DatabaseError(err))`, or return your own `httpapi.NewError` when the handler knows better. Never put driver text (`PgError` fields, SQL, connection details) in messages or `Details`, and don't classify by error strings: use `database.Classify`.
- Go: read configuration only through `internal/config`. Add new variables in `config.parse` using its `get(key, fallback)` helper, and validate them there: append each problem to the collected errors, which are returned together through `errors.Join`. Keep validation centralized in `parse`, never include secret values in errors, and pass other packages typed config structs (e.g. `config.Database`).
- Frontend: style with Tailwind utility classes. No other frontend conventions exist yet.

## 9. Git workflow and safety rules

- Default branch: `main`. Commit messages use the conventional-commit style (`chore: ...`).
- Real `.env` files hold local secrets and must never be committed. `.env` is gitignored.
- `.env.example` files hold safe placeholder values and should be committed.
- Keep the example env files (root `.env.example` and `backend/.env.example`) in sync with the variables the app actually reads (`backend/internal/config/config.go`, `docker-compose.yml`). When you add, rename, or remove a variable, update both example files in the same change.
- Never print or echo values from `.env`.
- Don't run destructive commands without explicit approval. That includes `docker compose down -v`, which deletes the `postgres_data` volume, `git reset --hard`, and force pushes.
- Don't install packages, commit, push, or create branches unless the user asks.
- Ignored local clutter you shouldn't rely on: `.history/`, `frontend/*.backup`, `frontend/npm-audit.json`, `.nuxt/`, `.output/`.

## 10. Known issues

1. The backend loads `../.env` relative to the working directory, and a missing default file is silently ignored. If you start it from anywhere other than `backend/` without setting `ENV_FILE`, it fails with "POSTGRES_DB is required" (and similar errors).
2. `@nuxt/eslint` is installed but not configured.
3. `frontend/README.md` is still the Nuxt starter template.
